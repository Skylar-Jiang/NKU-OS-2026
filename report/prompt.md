## 二、关键问题一：Lab2 内存管理如何接入 Lab3

### 分析重点

继承代码时，需要同时考虑分配算法和运行条件。Lab3 的分配接口增加了中断状态保存与恢复，整体覆盖为 Lab2 的包装函数会丢失这层保护。Page Init 还需要统一物理内存边界，避免把虚拟地址常量直接当成物理上限。

版本依据为小组仓库 `Skylar-Jiang/NKU-OS-2026` 的 `lab2` 分支、提交 `8b06753`，这是本轮实际查询并核对的版本。

### 模块设计约束

```text
[PROMPT]
参考小组已完成的 Lab2 实现，补齐 Lab3 中 Page Init 与 Best-Fit 的继承部分。
重点核对内存边界、空闲链表维护和 Lab3 的中断保护，并给出验证依据。

[RELY]
Lab2 参考版本为 origin/lab2@8b06753。
目标为 RV64，页大小为 4096 字节，DTB 提供物理内存范围。
Page 数组对应的物理页号区间为 [nbase, npage)。
调用者提供合法的分配和释放参数，当前实验采用单 hart 配置。

[GUARANTEE]
固件、内核映像、页描述符数组及其对齐空间不进入可分配页集合。
Best-Fit 选择最小的足够空闲块，大小相同时选择较低地址。
空闲块按地址排列，拆分、释放、合并后的计数和块头标记一致。
分配接口退出时保留调用前的中断使能状态。

[SPECIFICATION]
检查 DTB 范围及地址加法溢出，按 PHYSICAL_MEMORY_END 确定管理上限。
检查描述符数组占用，先标记保留区域，再登记合法的完整空闲页。
只将空闲块头挂链；释放时按地址插入并判断前后块是否物理相邻。
保留 local_intr_save/local_intr_restore，不改变框架自检和评分规则。
通过定向案例、独立位图参考模型和不同 RAM 配置核对结果。
```

### 理解与自查

- **`npage` 表示什么？** 它是物理页号的排他上界，描述符数量为 `npage - nbase`，不能把两者混用。
- **链表相邻能否直接合并？** 还要满足前块结束地址等于后块起始地址；链表顺序只用于寻找候选邻居。
- **为什么不能结束时一律开中断？** 调用前可能已经关中断，无条件开启会破坏外层临界区。
- **为什么增加独立参考模型？** 总页数正确仍可能选错块。对照返回地址和每次操作后的状态，才能识别误写成 First-Fit、漏合并和挂链错误。

## 三、关键问题二：Trap 处理后如何恢复原执行现场

### 分析重点

输入源码包中的 `RESTORE_ALL` 和 `__alltraps` 已有实现，本轮需要核对它们与保存过程是否对应，并验证实际行为。已有实现不能仅凭形式判断正确，也不能描述为本轮从空白开始完成。

RV64 下保存区共 36 个槽位，每槽 8 字节，总大小为 288 字节。原 SP 保存在槽 2；当前 SP 在恢复过程中仍用于访问保存区，因此必须最后恢复。`s1`、`s2` 暂时用于写回 CSR 后，还要恢复各自原来的通用寄存器值。

### 模块设计约束

```text
[PROMPT]
对照给定 SAVE_ALL 和 struct trapframe，核对 RESTORE_ALL、__alltraps、
__trapret 的实现，补充必要的布局检查，并验证 Trap 进入和返回的完整流程。

[RELY]
沿用给定 SAVE_ALL、结构体字段及 trap(struct trapframe *tf) 接口。
目标为 RV64；进入 Trap 前内核栈有效且满足 16 字节对齐。
C 处理函数负责中断/异常分发，以及必要的 tf->epc 调整。

[GUARANTEE]
a0 指向当前 Trap frame，作为 trap() 的第一个参数。
C 函数返回后进入 __trapret，从对应槽位恢复状态和通用寄存器。
恢复原 SP 后，通过 sret 返回 Trap frame 指定的位置和特权状态。

[SPECIFICATION]
不修改 SAVE_ALL、结构体字段及函数签名。
从槽 32、33 读取 sstatus、sepc，写回 CSR 后再恢复临时使用的通用寄存器。
通用寄存器按保存位置恢复，原 SP 最后恢复；x0 不需要回写。
scause/stval 保留作诊断快照，不作为本实验常规返回流程的回写目标。
底层统一返回代码不自行给 epc 加固定偏移。
增加布局编译检查，通过 GDB 比较保存值、恢复值和返回位置。
```

### 理解与自查

- **硬件已经保存了全部寄存器吗？** 硬件记录返回 PC、原因等 CSR 并更新部分状态；通用寄存器的栈上保存由汇编完成。
- **为何 Trap 要保存调用者保存寄存器？** 被打断代码没有主动发起一次 C 调用，不能要求它事先保存临时值。
- **为什么返回位置要从 `tf->epc` 取？** C 层可能按异常指令长度调整它；时钟中断则通常保留原返回位置。
- **为什么不能只比较整个 `sstatus`？** Trap 进入和 `sret` 会更新硬件管理位，应按各位的语义检查。
- **是否已经包含用户态栈切换？** 本轮验证针对当前 S 态内核栈，不能由此推导出完整的用户态切换、嵌套中断或多核支持。

### 从实际问题中明确的检查方法

**先区分工具错误和内核错误。** 首次评分受脚本 CRLF 换行影响，GDB 表达式也曾因直接对指针类型的 `$sp` 取模而报错。应先查看具体错误来源，再修正换行或表达式类型；这些现象不能直接归因于分配器或 Trap 恢复失败。

**按实际版本解释寄存器。** 初版检查假定 `sret` 后 SPIE 必为 1，但本机 QEMU 4.1.1 的结果不符。核对其 `helper_sret()` 后确认该版本会清零 SPIE，因此验证条件按实际版本修正，内核恢复代码没有为迎合错误预期而改写。

**把测试覆盖范围说清楚。** 评分通过是一个检查结果。寄存器恢复、不同长度异常、未知原因分支和挑战任务仍需要各自的验证。甲部分的显式 32 位断点测试用于检查底层现场恢复，乙、丙完成后还需要整组集成验收。
