## 1. First-Fit：实现路径与改进空间

当前 First-Fit 位于 `kern/mm/default_pmm.c`，管理器只接收 `page_init()` 交给它的空闲描述符范围。空闲块通过 `free_area_t.free_list` 的循环双向链表维护，块头 `Page` 的 `property` 保存块大小（页数），`nr_free` 保存空闲页总数。分配从链表头向后扫描，选第一个 `property >= n` 的块；有剩余时拆分并把余块插回地址有序链表。释放时按地址插入，再尝试与左右相邻空闲块合并。

设空闲块数为 k、释放区间页数为 n：分配的首次适配扫描和释放的插入点查找最坏都是 O(k)，释放还要清理 n 个描述符；找到位置之后拆分/合并是 O(1)。该策略简单，地址有序便于合并，但空闲块多时线性扫描较慢；不同大小请求交错还可能产生外部碎片，使总空闲页够用却没有足够大的连续块。

可按需求逐步改进：

- **Next-Fit**：记住上次命中位置，从该位置继续扫描，减少反复从表头扫描；最坏仍为 O(k)，分配顺序会影响碎片。
- **按大小分级的空闲链表或位图**：把常见块长分桶，先定位合适的桶，缩短搜索；需要维护桶间迁移、拆分和合并。
- **按地址组织的平衡树 + 大小索引**：用地址索引快速找到释放区间的前后邻居，用大小索引寻找满足请求的块；查询可做到 O(log k)，但元数据和实现复杂度更高。
- **Buddy**：按 2 的幂大小分阶，伙伴地址可用页号异或计算，分配/合并搜索阶数较少；代价是请求向上取整造成内部碎片。

若课程目标是理解基本分配器，保留 First-Fit 更合适；若主要瓶颈是大量空闲块的查找，优先考虑分级索引，而不是只凭算法名称替换。

## 2. 硬件物理内存如何探测

内核一般不靠向未知物理地址盲目读写来“试出”RAM 容量，因为地址可能不存在、发生别名、命中 MMIO 或有读写副作用。硬件/固件先枚举可用 RAM 和保留区，再通过标准接口传给内核：RISC-V 常见启动方式由 OpenSBI/引导程序传入设备树（DTB），其中 `/memory` 的 `reg` 属性描述内存区间；PC 平台常见 UEFI memory map 或 ACPI/固件表。内核解析后还要扣除固件、内核、页表、DTB、设备映射及保留内存区域，并对边界和页对齐作检查。

本实验的 `dtb_init()` 从 QEMU `virt` 平台 DTB 取得 memory base/size，当前代码按一个连续 DRAM 区间管理；这不等价于覆盖多段 RAM、内存热插拔和全部 reserved-memory 设备树节点的通用探测实现。

## 3. QEMU 4.1.1 宿主 GDB 调试

### 3.1 Bare 模式与 load/store

用 `host-load-store-bare.log` 在 QEMU 宿主 GDB 的 `riscv_cpu_tlb_fill()` 观察实际访问：

- OpenSBI M 态 load：VA `0x80009610`，`access_type=MMU_DATA_LOAD`、`mmu_idx=3`。
- OpenSBI M 态 store：VA `0x8001be00`，`access_type=MMU_DATA_STORE`、`mmu_idx=3`。
- uCore S 态 store：VA `0x80206000`，`access_type=MMU_DATA_STORE`、`mmu_idx=1`。
- uCore S 态 load：VA `0xffffffffc0202998`，`access_type=MMU_DATA_LOAD`、`mmu_idx=1`。

另在 `get_physical_address()` 返回后截取一条 Bare M 态 load，`host-bare-translation.log` 实测 VA=PA=`0x80009610` 且 `ret=0`。QEMU 4.1.1 的 `target/riscv/cpu_helper.c` 对 M 态访问直接令 `*physical = addr`；`mmu_idx=3` 对应 M 态。本例不走 S 态 Sv39 页表遍历。

### 3.2 S 态 Sv39 load 地址翻译

`host-sv39-load-translation.log` 对一次实际 S 态 load 单步读取页表：

- VA `0xffffffffc0202998`，`access_type=0`（load），`mmu_idx=1`（S 态）；SATP=`0x8000000000080205`，MODE=8，即 Sv39；根页表物理地址 `0x80205000`。
- `VPN[2]=0x1ff`，根级 PTE 地址 `0x80205ff8`，PTE=`0x200000cf`。其中 `PPN = PTE >> 10 = 0x80000`，`ptshift=18`，这是根级 1 GiB 叶映射，故本次在第一层就命中叶 PTE。
- 虚拟地址低 30 位并入叶映射：物理页地址 `0x80202000`，页内偏移 `0x998`，最终 PA=`0x80202998`。

该映射不是“每次访问都遍历三级表”；Sv39 最多三级，遇到叶 PTE 可在更高层映射更大页。原始翻译日志与 TLB-fill 的访存类型日志配套保存。

### 3.3 QEMU 主 TLB 与 victim TLB

`host-tlb-hit.log`（由 out-of-tree 调试版复跑）在 QEMU `accel/tcg/cputlb.c:get_page_addr_code()` 中观察到同一内核代码 VA `0xffffffffc02000d8`：第一次 `entry->addr_code=0xffffffffffffffff`，主 TLB 未命中，进入 `VICTIM_TLB_HIT`/填充路径；随后同一 VA 再次查询时，`entry->addr_code=0xffffffffc0200000`，页号匹配并走主 TLB hit 路径。

`host-victim-tlb.log`（同一 out-of-tree 调试版）则捕获到一次**实际 victim TLB 命中**：`victim_tlb_hit()` 的 `page=cmp=0x80000000`、`vidx=0`、`index=0`、`mmu_idx=3`；调用者为 `get_page_addr_code()`。函数接下来交换 victim 与主 TLB 项及对应 IOTLB 项。这说明 victim TLB 用于主表直接映射位置冲突后的补充查找，命中时可避免重新执行完整填充路径。

这里的主 TLB 和 victim TLB 是 QEMU TCG 为模拟客户机访存而维护的软件缓存结构，不是对真实处理器硬件 TLB 容量、时序和替换策略的逐周期仿真。真实 RISC-V TLB 属于处理器微结构；架构要求软件看到正确的地址翻译、权限和 `sfence.vma` 等语义。QEMU 以软件页表遍历和软件 TLB 缓存实现这些可观察语义，内部替换行为不代表某一真实芯片的 TLB 组织。

## 4. 独立构建带调试信息的 QEMU 4.1.1

没有覆盖课程现有 QEMU，也没有执行 `make install`。源码副本与真正的 out-of-tree 构建目录分开：

```bash
mkdir -p ~/riscv/qemu-4.1.1-lab2-debug-src
cp -a ~/riscv/qemu-4.1.1-src/. ~/riscv/qemu-4.1.1-lab2-debug-src/
# 该源码副本若带有已有的源码树内构建产物，先在副本内清理；原源码和课程 QEMU 不动。
cd ~/riscv/qemu-4.1.1-lab2-debug-src
make distclean
# 本次副本原有 riscv32-softmmu/riscv64-softmmu 是 make distclean 未移除的生成目录，已逐项确认后清理。
rm -rf -- riscv32-softmmu riscv64-softmmu
mkdir -p ~/riscv/qemu-4.1.1-lab2-debug-build
cd ~/riscv/qemu-4.1.1-lab2-debug-build
env -u CFLAGS ~/riscv/qemu-4.1.1-lab2-debug-src/configure \
  --target-list=riscv64-softmmu --enable-debug --disable-werror
make -j2
```

构建后使用：

```bash
file riscv64-softmmu/qemu-system-riscv64
./riscv64-softmmu/qemu-system-riscv64 --version
gdb -q riscv64-softmmu/qemu-system-riscv64
(gdb) info source
(gdb) info line riscv_cpu_tlb_fill
```

验证结果：真正的单独 build 目录构建成功，版本 4.1.1；二进制带 `debug_info`、未剥离；`info source`/`info line` 能定位 QEMU 源文件行；构建配置 CFLAGS 为 `-g`、没有 `-O`，GCC 默认不启用优化；新二进制已实际启动集成内核，OpenSBI 和 uCore 检查均成功。证据：`qemu-debug-outof-tree-configure.log`、`qemu-debug-outof-tree-build.log`、`qemu-debug-file-version.txt`、`qemu-debug-outof-tree-gdb-source.txt`、`debug-qemu-outof-tree-make-qemu.log`。

曾尝试显式 `CFLAGS='-O0 -g3'`，该旧版 QEMU 在启动阶段于 `notifier_list_add()` 崩溃；记录见 `debug-qemu-crash-gdb.log`。随后使用上面的 `--enable-debug` 默认调试配置成功构建和启动。不要把该构建参数导致的崩溃误报为 uCore 内核 Bug。
